# Values 1 and 2 on real Fineract output

Two claims about a distilled spec, tested against a real bank codebase: that a complete spec
lets you **change code with confidence** (value 1), and that it can **find divergence between
spec and implementation** (value 2). Both needed one new capability, and both now have data.

## The enabler: an arithmetic monitor that connects the spec to running code

Until now the spec could only be checked against itself. To check the code, you run the code,
record what it produces, and check that record against the spec. The v4 monitor did this for
boolean and temporal invariants but honestly skipped arithmetic, so every load-bearing loan
invariant was skipped. The new `monitor-schedule` evaluates arithmetic and quantified
invariants (`every`, `sum`, `follows`, `is_last`, `+ - *`, comparisons) over a concrete numeric
trace, and reports per invariant whether it holds and the **worst residual** — so an exact law
is distinguishable from one that only holds up to rounding. This is also the observability and
monitoring capability we had flagged as untested.

The substrate: **150 real schedules** generated by driving Fineract's own
`ProgressiveEMICalculator` over a grid of disbursed amounts, interest rates, and terms (1 to 24
months), emitted as traces with a manifest. Not a reimplementation; the real code.

## Value 2: the distilled invariants are exact laws of the real code

Running the monitor over all 150 real schedules:

    invariant            held/total   verdict
    principal_split      150/150      EXACT law (residual 0)
    conservation         150/150      EXACT law (residual 0)
    closes_to_zero       150/150      EXACT law (residual 0)
    emi_constant         125/125      EXACT law (residual 0)
    balance_rolls        125/125      EXACT law (residual 0)
    balance_monotonic    125/125      EXACT law (residual 0)

No divergence beyond a rounding unit on any schedule, so **no code bug surfaced**. That is the
expected outcome for a mature, well-tested calculator, and it is the honest result: the value-2
method is sound, and on this codebase it returns a clean bill rather than a manufactured bug.

The positive finding is sharper than "no bug". Every load-bearing law holds **exactly**, to the
penny, across every schedule, including the ones with a rounding-adjusted final instalment (EMI
91.68 for eleven periods, 91.66 on the last). Conservation holding exactly under 2-decimal
rounding means Fineract absorbs its rounding into the final instalment so the principals still
sum to the disbursed amount and the loan still closes to zero. That is a real, non-obvious
property of the implementation, now machine-checked against a written spec rather than assumed.
The 125 counts are the multi-period schedules; single-period loans have no follows-pairs, so
those invariants have no instances to check there (correctly reported, not skipped silently).

One honest gap: `interest_on_outstanding` (interest = rate × balance) is the one invariant not
checked here, because the traces omit the per-period rate factor. It is also the one invariant
we expect to hold only up to rounding, so it is the natural next thing to instrument.

## Value 1: the spec as a standing regression gate

The same monitor, used as a gate: take each real schedule, inject a realistic behaviour-breaking
change (the kind a feature edit could introduce), and see whether the gate catches it and names
the right law. No-op mutations (e.g. dropping a rounding adjustment on a zero-interest loan that
never had one) are excluded, not counted as misses.

    baseline (no mutation): gate passes 150/150 real schedules — 0% false alarms

    mutation             applicable  caught     names the right law
    drop_final_rounding  96          96/96      96/96
    penny_leak           125         125/125    125/125
    interest_tweak       150         150/150    150/150
    neg_amortisation     125         125/125    125/125

Every injected break is caught on every schedule, with the violated invariant named and an exact
residual, and with **no human or model in the loop**. That is the "change code with confidence"
property stated as a result: after a change you regenerate schedules, run the gate, and it tells
you precisely which behavioural law broke and by how much.

### The differential: does a capable model catch these anyway?

The interesting question is whether the deterministic gate adds anything over a capable model
reviewing the output. The subtle case is `penny_leak`: a 0.01 discrepancy buried in a table of
up to 24 rows. We asked the model to review each schedule in-head (no tools, so it must reason,
not compute), without naming the invariant, and say VALID or BROKEN.

## Honest limits

- No real bug was found. Mature code, and the injected-mutation study is what demonstrates the
  gate has teeth; a found bug would have been a bonus, not the basis of the result.
- The monitor is bounded per schedule (it evaluates concrete traces, it does not prove properties
  for all inputs). Value 2's confidence comes from breadth of real inputs, not a proof.
- One subsystem of Fineract, not whole-system scale. The scale frontier — where behaviours exceed
  one context — is still only approached, not reached.
- `interest_on_outstanding` was not checked (rate factor not in the traces).

## What this says for the objective

Value 2 turns the earlier completeness finding into a standing check: the distilled invariants
are not idealisations, they are exact laws the real code obeys, verifiable on demand. Value 1
makes the assurance concrete: a deterministic gate that catches behaviour-breaking changes and
names the law, with zero false alarms on real output. The differential arm is where the
non-saturation lives — the gate does not depend on a reviewer's attention holding over a long
numeric table, which is exactly where a helpful, capable model quietly lets a penny through.
