## How a goodwill credit reaches accounting

A goodwill credit is created as a repayment‑type transaction, not a bespoke posting type. `LoanGoodwillCreditCommandHandler` routes it through `makeLoanRepayment(LoanTransactionType.GOODWILL_CREDIT, …)` (`fineract-loan/.../handler/LoanGoodwillCreditCommandHandler.java:47`), and `LoanTransactionType.isRepaymentType()` returns true for it (`fineract-loan/.../domain/LoanTransactionType.java:194`).

Postings are then generated by the accounting bridge in `JournalEntryWritePlatformServiceJpaRepositoryImpl` (around line 541‑547), which selects a processor via `AccountingProcessorForLoanFactory.determineProcessor` (`.../AccountingProcessorForLoanFactory.java:32‑47`): cash‑based or accrual‑based. Both classify goodwill credit as a repayment and dispatch to their repayment methods (cash dispatch at `CashBasedAccountingProcessorForLoan.java:81‑83`).

## Every place that must emit postings

For a standard loan there are four branches, one per (cash|accrual) × (normal|charged‑off):

- Cash, normal: `CashBasedAccountingProcessorForLoan.createJournalEntriesForLoanRepayments` — goodwill legs at `:750, :760, :782, :805, :816` and the debit emission at `:830‑836`.
- Cash, charged‑off loan: `createJournalEntriesForChargeOffLoanRepayments` — goodwill legs at `:572, :600, :627, :655, :681`.
- Accrual, normal: `AccrualBasedAccountingProcessorForLoan.createJournalEntriesForLoanRepayments` — goodwill legs at `:1723, :1740, :1776, :1806, :1823` and debit emission at `:1847‑1852`.
- Accrual, charged‑off loan: `createJournalEntriesForRepaymentWhenLoanIsChargedOff` — goodwill legs at `:1433, :1461, :1491, :1529, :1564`.

Reversal is handled generically: a reversed goodwill transaction short‑circuits to `createJournalEntryForReversedLoanTransaction` (`CashBasedAccountingProcessorForLoan.java:69‑71`), which mirrors the original balanced legs.

There is also a separate, parallel subsystem for the working‑capital loan product that must emit its own goodwill postings: `AccrualWithDeferredRevenueAmortizationAccountingProcessorForWorkingCapitalLoan.postGoodwillCreditJournalEntries` (`fineract-provider/.../AccrualWithDeferredRevenueAmortizationAccountingProcessorForWorkingCapitalLoan.java:114‑127`), dispatched from the `GOODWILL_CREDIT` case at `:80‑86`, with its own command builder (`CommandWrapperBuilder.java:1272`). This does not share the standard processors' machinery.

## What guarantees the postings balance

Nothing at runtime. The persistence path writes each leg independently: `AccountingProcessorHelper.createCreditJournalEntryForLoan` / `createDebitJournalEntryForLoan` build one `JournalEntry` and call `persistJournalEntry` with no debit‑equals‑credit check (`AccountingProcessorHelper.java:934‑982`). The "total debits must equal total credits" rule exists only for the manual journal‑entry API (`JournalEntriesApiResource.java:78` and its command validator); system‑generated loan postings bypass that validator entirely.

Balance is therefore guaranteed only by construction, and by two different conventions depending on the branch:

- The charged‑off branches use `populateCreditDebitMaps` (`CashBasedAccountingProcessorForLoan.java:197`, `AccrualBasedAccountingProcessorForLoan.java:963`), which adds the same amount to both a credit map and a debit map for each money portion. Each portion is balanced because it is entered on both sides in one call.
- The normal branches post credits per portion, then mirror each portion into `debitAccountMapForGoodwillCredit` with the identical amount via `LoanCommonAccountingHelper.populateDebitAccountEntry` (`:104`). Balance holds because Σcredits = `totalDebitAmount` = Σ(goodwill debit map).
- The working‑capital method hand‑pairs the two sides inline (debits: principal+overpayment, fees, penalties; credits: loan portfolio, fees receivable, penalties receivable, overpayment). It balances only because those two sums are arithmetically equal for the portions it handles.

The practical consequence: the invariant is convention‑enforced and fragile. Any new money portion added on only one side, or a mismatched amount, silently unbalances the ledger with no guard to catch it. The working‑capital processor is the weakest link here: it is a separate reimplementation that does not use the shared balance‑holder discipline, and it has no interest leg at all (`:114‑127` handles only principal, fees, penalties, overpayment), so it would need care if goodwill credits ever allocate to interest on that product.
