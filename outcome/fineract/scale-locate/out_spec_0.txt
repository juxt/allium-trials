## The loan posting path, end to end

**1. Bridge / entry point.** A posted loan transaction enters the accounting layer here:

- `LoanJournalEntryPosterImpl.postJournalEntriesForLoanTransaction` (`fineract-provider/.../portfolio/loanaccount/service/LoanJournalEntryPosterImpl.java:36`) delegates to
- `JournalEntryWritePlatformServiceJpaRepositoryImpl.createJournalEntriesForLoanTransaction` (`.../accounting/journalentry/service/JournalEntryWritePlatformServiceJpaRepositoryImpl.java:826`), which builds an `AccountingBridgeDataDTO` and calls
- `createJournalEntriesForLoan(AccountingBridgeDataDTO)` at `JournalEntryWritePlatformServiceJpaRepositoryImpl.java:540`. This builds the `LoanDTO` (`helper.populateLoanDtoFromDTO`), picks the regime with `determineProcessor`, and hands off to the processor. **No balance check happens here.**

**2. Leg splitting and posting.** The two regime processors split the transaction into typed legs (principal, interest, fees, penalties, overpayment) and post each side:

- `CashBasedAccountingProcessorForLoan.createJournalEntriesForLoan` (`.../service/CashBasedAccountingProcessorForLoan.java:52`) — reads `getPrincipal/getInterest/getFees/getPenalties` (lines 146-149) and calls the credit/debit primitives.
- `AccrualBasedAccountingProcessorForLoan.createJournalEntriesForLoan` (`.../service/AccrualBasedAccountingProcessorForLoan.java`) — the accrual twin.
- The posting primitives are `AccountingProcessorHelper.createDebitJournalEntryForLoan` / `createCreditJournalEntryForLoan` (`.../service/AccountingProcessorHelper.java:934` and neighbours). Each builds one one-sided `JournalEntry.createNew(... JournalEntryType.CREDIT/DEBIT ...)` with `manualEntry = false` and calls `persistJournalEntry` (line 946). **A single leg is one-sided by construction; nothing checks the sum.**

**3. Is debit=credit actually enforced on the loan path? No.** There are two checks in the codebase, and neither guards the loan posting path:

- `JournalEntryWritePlatformServiceJpaRepositoryImpl.checkDebitAndCreditAmounts` (`:306`) is the real global "sum of debits = sum of credits" assertion (`creditsSum.compareTo(debitsSum) != 0` → `DEBIT_CREDIT_SUM_MISMATCH`, line 323-324). But it is only reached from `validateBusinessRulesForJournalEntries` (`:626`) via `createJournalEntry` (`:146`) and the revert/update path (`:724`) — that is the **manual/API journal-entry path** operating on `SingleDebitOrCreditEntryCommand[]`. The loan processors never call it.
- `AccountingProcessorHelper.createJournalEntriesForLoanCharges` (`:427-441`) does throw if sums mismatch, but it checks each side against the *charge transaction total* independently (`totalAmount vs totalCreditedAmount`, `totalAmount vs totalDebitedAmount`), and only for the charge-distribution sub-case. It is not a transaction-wide debit=credit invariant over all legs.

So on the loan path the double-entry balance is **emergent, not enforced**: it holds only because each processor branch is hand-written to post matching debit and credit amounts for every leg. There is no assertion at the bridge, in the processors, or in the leg primitives that the summed debits equal the summed credits for a posted loan transaction. This matches the spec's observation that balance is "invisible at any one posting site."
