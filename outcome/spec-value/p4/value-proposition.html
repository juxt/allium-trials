What a spec is for, measured.

Every claim here is a mechanical number: a program built from a spec and diffed against 150 real loan schedules, or the checker's own pass/fail. Nothing was judged by a model.

The finding. A spec is necessary for correctness beyond what a model can guess, and that is the biggest win by far. But the spec's notation and the model's strength don't move one-shot correctness — v4, a prose spec and v3 tie, and a cheap model matches an expensive one. Allium v4's real, unique advantage is that the spec is executable: it can be mechanically checked and run as a standing regression gate that catches drift a prose spec cannot express or verify at all.

01A spec is necessary — clear air over no-spec

Ask a model to build a loan schedule for a product with a system-specific convention (add-on/flat interest) it can't guess. Without a spec it ships the textbook default (declining balance) and is wrong. With any spec it is right. Same story when the request is underspecified and the spec is elicited.

03The unique edge: an Allium spec is executable clear air over prose & v3

A prose spec is inert. An Allium v4 spec is machine-checkable (syntax + semantic faithfulness against the code's own traces) and runs as a deterministic regression gate. Take a correct implementation, apply developer edits, run the gate:

04"Why not just write tests?" — the honest answer

A test suite is executable too. So we ran the gate against two hand-written test suites over 137 real input rows and a mutation battery of developer edits. The result is honest, and it is not "specs catch more".

The gate equals a correctly re-implemented oracle test row for row — as a pure detector it is no stronger. It beats structural tests on value bugs (0 vs 89–107), the same desync lesson. The real separation is the anchor: when a developer who believes flat interest is correct ships that build and writes the oracle test to match, the test passes — false confidence, 0/137 — while the spec, whose faithfulness is checked against the real system's recorded traces by construction, fires 89/137.

Stated honestly: a spec ties a correct test on raw detection. Its edge is that it anchors to reality by construction (can't silently encode a wrong belief), is one declarative statement over all rows with no second implementation to drift, and is auditable by a non-programmer.

05The language is getting better — each construct closes a real bug class

A behavioural gate can only catch what the language can express. This programme shipped the operators real financial specs need, and each measurably widened what the gate catches on real code.

division /

Was entirely missing — x/1200 silently became x. Now specs pin interest to a rate. Value-drift catch on 144 real traces: 0/144 → 144/144.

min / max & if/then/else

Caps/floors (fee = min(computed, cap)) and tiered values (if bal > 10k then 5 else 10) — the shapes real fee/rate products need.

temporal ordering

before over the event timeline. Payment sequencing (capture-after-authorize): 12/12 ordering bugs caught, 0 false positives.

reference definitions

given k means <expr> — absolute, input-anchored invariants. The difference between catching structural bugs only and catching wrong values too.

06Small core, contributable library — extensible, not fat

The design question: keep adding to the core, or let users contribute? The data says shrink the core. Given if/then/else + comparison + given f means e, the "built-ins" are USER-DEFINABLE and compose:

given min(a,b)  means if a < b then a else b
given clamp(x,lo,hi) means max(lo, min(x, hi))   -- composes; monitors; caught a cap breach

functions

User-extensible. A shared std.allium imported with use "path" resolves at check and monitor time. min/max/clamp/abs belong here, not the core.

types

Currency/unit tags already open: Money(gbp)≠Money(usd) caught, no core change per currency. New numeric families: a known mechanism, deferred until the corpus demands one.

substrate

Exact-decimal is the one place to grow the core (it's below user-space) — but tolerance already absorbs the code's rounding, so it's narrow. Reserve core growth for genuine primitives.

fluency

Data from distilled specs drove p.field = field(p) — the object.attribute form models write naturally. The core stays small; the ergonomics meet the author.

07What to build on it

  • Pitch: the spec you need for correctness (over no-spec), that stays true because it's executable (over prose/v3). Not "more correct or cheaper than prose" — that saturates.
  • Lean into: distillation + a standing gate over real production traces; each new operator opens a bug class to gate against; a small extensible core beats a fat one.
  • Honest limits: one-shot correctness is model- and notation-independent (v3 ≈ v4 ≈ prose, opus ≈ haiku); the gate needs the spec's reference inputs emitted in traces; the tolerance, not exact arithmetic, absorbs the code's rounding. Authoring is a distil → check → faithfulness → fix loop, and it is the canonical-form skill guidance — not a bigger grammar — that makes it converge (a fresh agent reached a valid spec in one round with the reference's translation table).
  • Against "just write tests": the gate ties a correct oracle test on detection and beats structural tests on value bugs; its edge is anchoring to real traces by construction, one declarative statement over all cases, and auditability — not raw detection power.
  • For ratification (data-backed): core — /, if/then/else, round, temporal, given/use; sugar — p.field, each=every, let, ==; demote min/max to the stdlib. Block-colon grammar fork: declined, steer via skill. 59 tests pass.
